# Extra — Explore: a plan rendered as interactive HTML

## What it adds

A markdown plan is the right artifact for an agent and a poor one for a human.
It is long, flat, and says "see `server/services/foo.ts`" without showing you
`foo.ts`. **Explore** turns a task's plan into something a person can actually
review: a **self-contained, interactive HTML page** generated by an agent that
has read both the plan and the code it cites, displayed next to a read-only view
of the repository.

One click on a task's **Explore** button opens an IDE-like page:

```
┌──────────────┬───────────────────────────────────────────────┐
│  file tree   │  [ Schema ] [ foo.ts ] [ bar.ts ]             │
│              │                                               │
│  read-only,  │   the generated HTML artifact                 │
│  the task's  │   (sandboxed iframe) — or a source file,      │
│  worktree    │   scrolled and highlighted by the agent       │
│              ├───────────────────────────────────────────────┤
│              │  chat with the generating agent (refine it)   │
└──────────────┴───────────────────────────────────────────────┘
```

The artifact comes in three **kinds**, and a task can hold one of each:

| Kind | What it is |
|---|---|
| `plan` | The task's plan as a navigable page: phase cards, decision callouts, a testing block. The writing stays close to the source plan. |
| `flowchart` | A hand-authored SVG of how a request or key operation moves through the code, with chips that light up and animate the path. |
| `architecture` | A full-screen SVG map of the modules a feature touches, with clickable nodes. |

Every artifact has rich click-to-detail (clicking a phase or a node opens
several paragraphs, not a tooltip), follows the app's light/dark theme, and
makes every file reference clickable: the click opens that file, at that line,
in a tab beside the artifact. The first visit generates the `plan` kind
automatically; later visits show what is stored.

## Why it's an extra (not core)

Core only needs a plan the next agent can read. How a *human* reviews that plan
before pressing Run is a matter of taste — some teams read the markdown, some
read the diff later. Remove this extra and nothing in the loop changes: no agent
ever reads an artifact, and no workflow flag depends on one.

It is also the most harness-specific feature in the repo. It relies on handing
the model **in-process tools that act on the user's browser**, which the
reference only does through the Claude Agent SDK.

## The idea: the agent authors a document, the host just displays it

There is no diagram schema, no layout engine, and no renderer in Bottega. The
agent writes **one complete HTML document** — CSS, JavaScript and SVG inlined,
zero external resources — and hands it over through a tool call. The host stores
the string and puts it in an iframe.

This is the whole trick, and it is why the output is good. A model is far better
at writing a bespoke page for *this* plan than at filling in a generic diagram
format, and a standalone document needs no build step and cannot break when the
app changes. The cost is that you are displaying model-authored HTML with
scripts in it, so the isolation described below is not optional.

Quality comes from two things in the prompt
([`../reference/server/constants/prompts/atlas-artifact.md`](../reference/server/constants/prompts/atlas-artifact.md)):

- **Exemplars, not adjectives.** The prompt does not describe good design. It
  points the agent at a handful of gold-standard HTML files shipped with the app
  and tells it to read the ones matching the requested kind *before* authoring.
  The files are vendored under
  [`../reference/server/constants/atlas-style-refs/`](../reference/server/constants/atlas-style-refs/)
  (a curated subset of the open-source `effective-html` corpus — see `NOTICE.md`
  there for attribution and licences). Their directory is passed in as a prompt
  variable, resolved from the install location (`getAtlasStyleRefsDir` in
  [`../reference/server/services/promptRenderer.ts`](../reference/server/services/promptRenderer.ts)).
- **Read the code, not just the plan.** The agent is told to open the files and
  symbols the plan cites until the structure it draws is real. A diagram built
  from the plan's prose alone is a guess.

The prompt also fixes the conventions every artifact must follow: theme through
CSS variables with a `dark` class, an apply-before-paint theme script, every
`localStorage` access wrapped in `try/catch` (see the sandbox section for why),
and the two `postMessage` messages below.

## The three tools

Generation is an ordinary task conversation with one difference: it carries an
extra, in-process tool server named `code-atlas`. `buildAtlasMcpServer` in
[`../reference/server/services/atlas/mcpServer.ts`](../reference/server/services/atlas/mcpServer.ts)
builds it per turn, closed over the task id, with three tools:

- **`render_artifact({ html, kind, title? })`** — the deliverable. Validates,
  stores, and displays the document.
- **`open_file({ path, line? })`** — opens a workspace-relative file in the
  viewer, optionally scrolled to a line.
- **`highlight({ path, ranges, color? })`** — paints line ranges in a file.

The last two exist for the follow-up conversation: the user asks "where is the
closure check?" and the agent *shows* them, instead of quoting code into chat.

`render_artifact` validates **before** it touches anything: the string must look
like an HTML document, and it is capped at 512 KB. A rejected call returns an
error the agent can act on ("trim the artifact") and leaves the previous
artifact of that kind intact. A bad generation never destroys a good one.

## Tools that act on a browser: the ack bridge

The tools run on the server but their effect is in the user's browser tab. A
tool that returns "opened `foo.ts`" when no tab did so teaches the agent to
narrate things the user cannot see. So each tool call is a round trip:

1. The server tags the command with a request id and broadcasts it to every
   Explore view subscribed to that task.
2. The view applies it — opens the tab, paints the highlight, mounts the iframe
   — and sends back an **ack** carrying the id.
3. The tool resolves on the first matching ack, or fails on timeout (5 s; 15 s
   for an artifact, which has to mount a large document).

See `sendAtlasEvent` in
[`../reference/server/services/atlas/bridge.ts`](../reference/server/services/atlas/bridge.ts)
and its client half, `useAtlasEvents` in
[`../reference/src/components/atlas/useAtlasEvents.ts`](../reference/src/components/atlas/useAtlasEvents.ts).
The bridge knows nothing about sockets: the broadcaster and the subscriber
counter are injected at boot (`initAtlasBridge`), which also keeps it testable.

**When nobody is watching**, the behaviour splits on purpose. Generation takes
minutes and users close tabs, so `render_artifact` with zero subscribers still
validates and **persists** — the artifact is there on the next visit. The two
pointing tools have nothing durable to do, so they return a polite note saying
no view is open. When a view *is* open, `render_artifact` persists only after
the ack, so a document the browser failed to mount is never saved.

## Displaying model-authored HTML safely

The artifact is rendered by assigning it to an iframe's `srcdoc` with
`sandbox="allow-scripts allow-popups"` and, crucially, **without
`allow-same-origin`** — see
[`../reference/src/components/atlas/AtlasArtifactView.tsx`](../reference/src/components/atlas/AtlasArtifactView.tsx).
That gives the document an opaque origin: its scripts run, but it cannot read
the app's cookies, storage or DOM, and it cannot call the API as the user.

Two consequences shape the rest of the design:

- **The artifact must be self-contained.** With no usable origin there is
  nothing to load from, which is why "zero external resources" is a hard rule in
  the prompt and not a style preference.
- **`localStorage` throws** inside an opaque origin. An artifact that reads it
  unguarded renders a blank page — hence the `try/catch` rule.

Host and artifact talk through exactly two `postMessage` shapes:

| Direction | Message | Effect |
|---|---|---|
| artifact → host | `{ type: 'bottega-open-source', path, line? }` | open that file in a tab, at that line |
| host → artifact | `{ type: 'bottega-theme', theme }` | switch light/dark |

The host cannot check `event.origin` (it is the string `"null"` under the
sandbox), so it gates on **identity** — `event.source` must be this iframe's
window — and on message shape. And the requested path is only ever a *request*:
it goes through the same containment-checked file read as everything else.

The HTML itself never travels in a URL. The view fetches it over the
authenticated API when a kind becomes active.

## A read-only, contained view of the repository

All file access — the tree, the viewer, and both pointing tools — goes through
one class, `Workspace` in
[`../reference/server/services/atlas/workspace.ts`](../reference/server/services/atlas/workspace.ts):

- **Containment in one place.** Every path is resolved against the root and
  rejected if it escapes. Nothing else touches the filesystem.
- **Read-only.** There is no write method. Explore is a reading surface.
- **Same root as a conversation.** `getWorkspaceForTask` picks the task's
  worktree when one exists and the project repo otherwise — the same rule
  conversations use — so the user sees exactly the code the agent sees.
- **Reading-surface limits.** Files over 2 MB and binary files are refused with
  a message rather than rendered.
- **No absolute paths leave the server.** Payloads carry workspace-relative
  paths only.

The workspace is resolved lazily on every tool call, not once per conversation,
so a worktree created or removed between turns is always reflected.

## Generation: one conversation, started idempotently

`POST /api/tasks/:id/atlas/generate-artifact` (in
[`../reference/server/routes/atlas.ts`](../reference/server/routes/atlas.ts))
creates a normal task conversation, marks it `atlas_enabled`, and starts it with
the rendered prompt. Three decisions are worth copying:

- **The flag lives on the conversation row.** The tool server is attached
  whenever a turn starts on a conversation with `atlas_enabled` set
  (`withAtlasMcpServer` in
  [`../reference/server/services/conversation/atlasInjection.ts`](../reference/server/services/conversation/atlasInjection.ts)).
  Because the row is the source of truth, a resumed turn or a retry re-attaches
  the tools without the caller knowing how the conversation began — which is
  what makes follow-ups ("redo it as an architecture diagram") work in the same
  thread.
- **One generation per task at a time.** A plan artifact takes minutes, and the
  page's auto-generate effect re-runs on every fresh mount. If a generation is
  already streaming for the task, the endpoint returns *that* conversation
  instead of starting another (`getOngoingAtlasGenerationConversationId`). The
  client treats both answers the same.
- **Show before generate.** On entry the page lists the task's stored artifacts
  and decides: a `plan` exists → show it, spending nothing; none → generate.
  The rule is a pure function, `decideSchemaEntry` in
  [`../reference/src/components/atlas/schemaEntryDecision.ts`](../reference/src/components/atlas/schemaEntryDecision.ts).

The request body carries only the kind — a concrete one, or `auto` to let the
agent choose the best fit for the task. The model is not chosen in the page: it
comes from a dedicated per-user setting (the `schema` key, see
[`./prompt-and-model-customization.md`](./prompt-and-model-customization.md)),
and a user with no valid setting gets an error rather than a silent default.

Storage is one row per `(task, kind)` — the `task_artifacts` table in
[`../reference/server/database/init.sql`](../reference/server/database/init.sql).
Regenerating a kind replaces it; a different kind adds a row. Artifacts are
deleted with their task.

## The page

`TaskIdePage`
([`../reference/src/pages/TaskIdePage.tsx`](../reference/src/pages/TaskIdePage.tsx))
is the three-pane layout sketched above: a lazy file tree, a tab strip with a
pinned **Schema** tab plus one tab per opened file (CodeMirror, read-only), and
a collapsible chat panel bound to the generating conversation.

The view state — which tabs are open, which is active, each file's highlights,
the current artifact — is a **pure reducer** (`atlasViewReducer` in
[`../reference/src/components/atlas/atlasTabsReducer.ts`](../reference/src/components/atlas/atlasTabsReducer.ts)).
Commands arriving from the agent and clicks from the user dispatch the same
actions, so the transitions can be tested without a socket or a browser.

## Why it is Claude-only in the reference

The tool server is created in-process with the Claude Agent SDK
(`createSdkMcpServer`) and handed to the SDK as a live object. The other
harnesses in the reference run out of process and cannot take one. So the
`schema` model setting is locked to Anthropic and the endpoint always creates an
Anthropic conversation.

That is a property of this implementation, not of the idea. To support another
harness, expose the same three tools over a transport it can reach (a local
stdio or HTTP MCP server) and keep everything else.

## When to install it

Install Explore when humans review plans before agents implement them, and the
plans are big enough that reading markdown is the bottleneck. It costs one extra
agent run per artifact (a few minutes on a capable model) and it makes you
responsible for sandboxing model-authored HTML correctly. Skip it if plans are
short, or nobody reads them before pressing Run.

## What to build

- [ ] A `(task, kind)` artifact store holding a title and an HTML document, and
      an `atlas_enabled` boolean on the conversation row.
- [ ] A read-only, containment-enforced workspace rooted where the task's
      conversations run, with size and binary guards.
- [ ] REST endpoints behind the same membership check as other task routes:
      list a directory, read a file, list artifact summaries, fetch one
      artifact's HTML, start a generation.
- [ ] A subscribe channel per task for Explore views, and a bridge that sends a
      command and awaits a matching ack with a timeout.
- [ ] The three tools, with validate-before-persist on `render_artifact` and
      the "persist even with no viewer" rule.
- [ ] Injection of the tool server on every turn of a flagged conversation,
      including resumes.
- [ ] The generation prompt and a small set of exemplar HTML files it points
      the agent at (mind their licences).
- [ ] An idempotent start endpoint that binds to an in-flight generation, and a
      show-before-generate rule on page entry.
- [ ] A sandboxed iframe **without same-origin**, plus the two-message
      `postMessage` contract with source-identity validation.
- [ ] The page: file tree, tabbed viewer with highlights, kind switcher, and a
      chat panel bound to the generating conversation.
